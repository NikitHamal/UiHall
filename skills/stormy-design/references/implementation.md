# From reference to implementation

A useful decision record is short:

| Evidence | Observation | Transfer | Authored choice |
|---|---|---|---|
| Asset ID opened in a viewer | Visible proportions, hierarchy, density | Principle useful for our task | How our product changes it |

Do not fill the observation column with a description you have not checked.
A reference can teach one useful principle without dictating the whole page.

For a reference library, the primary job is finding and inspecting work. Make
search, filters and media quality legible before adding decorative chrome. For a
transactional interface, prioritize the transaction and recovery states instead.

Define token roles for surfaces, text, accent, border, focus, spacing, radius and
motion. Author values to fit the brief; do not claim those values were measured.
Sampled palettes are input material. Contrast checks apply to the actual composited
foreground and background, including overlays, images and opacity.

Build components around state: each control should have a clear owner, result and
feedback. Handle empty matches, missing images, clipboard denial and unavailable
storage. Where state should survive refresh, persist it or encode it in the URL.
A local shortlist is not a cloud-synchronized board; tell the user which they have.

Verify the main journey at 360px, an intermediate width and desktop. Check long
labels, zoom, keyboard navigation and the final DOM's semantics. Use a native modal
dialog or implement focus containment and restoration. Focus must return to the
launcher when the dialog closes, including after stepping between references.

Critique in order of impact: task clarity, hierarchy, legibility, affordance,
spacing rhythm, state coverage and polish. Give a concrete change and explain
its effect. Avoid declaring one reference objectively better from metadata alone.
